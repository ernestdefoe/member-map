# Member Map: working rules

- **Commit straight to `main` and push. Never open a pull request on this repo.** Commit subjects are conventional (`feat:`, `fix:`); the release drafter bumps from the subject.
- `js/dist` is committed and is what forums load. After any change under `js/src`, run `npm run build` in `js/` (from a fresh `npm ci`) and commit the bundle; CI fails if it is stale.
- Publishing a release is Ernest's click. Nothing is announced until he says so.

## Design rules that exist for a reason

- **Privacy is enforced on the server.** A saved location is the centre of the named place (city, region or country) around the point the member chose, looked up by `Geocoder::place()` and rounded (`Precision::decimals`). The raw point is never stored or returned. Never add a path that saves client coordinates directly.
- **Nominatim's usage policy**: max one request a second for the whole forum (cache lock + timestamp in `Geocoder::throttle`), an identifying User-Agent, every answer cached 30 days in `member_map_geocode` (pruned daily by `member-map:prune`, not by the file cache, which never deletes expired keys), and **no search-as-you-type**: the form searches only on the button or Enter.
- 🚨 A request NEVER calls the geocoder: it answers from the cache, or queues `Job\LookUpPlace` and answers `member_map_busy` (429), and `api.ts` asks again every second (6 times). With the default sync queue the job has already run by the time the request re-checks the cache. The throttle (one call a second, `Geocoder::throttle`) lives in the job and never waits: a call too soon is dropped and the next ask queues it again. No `usleep`, no `lock->block()` (Floxum charged both on 1.0.1). Failures are logged in `Geocoder::lookUp` and rest the provider 30 s.
- Geocoding happens only when a member searches or saves. Never call it while rendering a page.
- **API shape**: places, trips and meetups are JSON:API resources (`member-map-locations` keyed by user id, `member-map-trips`, `member-map-meetups`), validated in their `creating()` hooks with `Api\Problem` (a KnownError whose type is the error `code`; its status is listed in extend.php's ErrorHandling). The widget's counts are a non-database resource too (`member-map-stats/map`). Only two read-only plain handlers stay, each saying why (docblock + README): the map's lean rows (`MapController`, which also narrows by `?group=` / `?following=1`) and the place lookup. Don't add more.
- **Permissions granted to "Everyone" are stored on the Guest group** and inherited by members: `MemberQuery::permitted()` counts Guest AND Member grants (1.0.1 sent trip alerts to admins only when the map was open to Everyone).
- **Frontend writes go through `app.store`** (models in `js/src/forum/models`, `Extend.Store`; `saveRecord`/`deleteRecord` in api.ts). A record for an existing id is PUSHED into the store (`pushObject`), never `createRecord` + `exists = true`: `Model.delete()` rejects for a record the store doesn't hold.
- **Optional extensions** (Suspend, Follow Users, Tags, Calendar, Page Builder, GDPR) are wired ONLY in extend.php's `Extend\Conditional`: a default class in `src/Integrations` that does nothing, swapped by `Extend\Binding` for the version that uses the other extension (or a listener on `MeetupPlanned` for Calendar). No `isEnabled()`/`class_exists()` in `src/`. Every one is in composer.json's optional-dependencies and suggest.
- extend.php uses string setting keys, never `Settings::` constants (it is read on every boot, also mid-deploy). Emptied tile/credit/geocoder addresses are deleted on save (`ForgetClearedSettings`) so `->default()` applies; nothing reads them with a fallback.
- Trip alerts go out from a queued job (`NotifyNearbyMembers`), never the request.
- The map endpoint is ONE query (`MemberQuery`): visibility, confirmed email, the `member-map.list` permission (checked in SQL via group_permission/group_user, so losing it takes someone off the map at once) and suspension.
- `memberMapLocation` / `memberMapOwn` on the user resource are deferred values batched per request (`Api\UserFields`): one query for every user on the page. Keep state keyed by the request in the WeakMap.
- The map engine is MapLibre GL 6 (OpenFreeMap vector styles; raster tiles as the fallback), the `forum/map/engine` chunk, imported dynamically. A STATIC import of it from two chunks makes webpack emit a numbered root chunk that `jsDirectory` does not publish (404). MapLibre 5.x has a critical sanitizer advisory: stay on 6.
- MapLibre 6 needs its module worker. 🚨 It is bundled INSIDE the engine chunk as a string (`?worker-source` → `js/scripts/worker-source-loader.cjs`) and `engine.prepare()` starts it from a blob. Never ship it as a separate file again: a forum left `maplibre-worker.js` unpublished (404, blank map, reported by Claudius 2026-11-12). The loader drops the worker's `//# sourceMappingURL` comment because Flarum strips that comment to end-of-line from every chunk, which would cut the one-line string. `MapAssetsTest` guards both. Await `prepare()` before creating a map; if the engine can't start, the page shows the list with a note (`mapFailed`).
- Its CSS is injected by the chunk (`map/mapCss.ts`, generated by `scripts/map-css.mjs`), not in forum.less.
- 🚨 Flarum sends `Referrer-Policy: same-origin`, so tile requests carry no Referer and OpenStreetMap answers with an "Access blocked" picture. The engine's `transformRequest` and the profile mini-map's `<img referrerpolicy>` send the origin.
- MapLibre writes `transform` on a marker's element: our buttons sit inside a `.MemberMapMarker` wrapper so hover zoom and the drop-in animation never fight it.
- `map.loaded()` stays false while any tile loads: use our own `ready` flag (set on the first `load`). The globe's zoom is the Mercator zoom at the centre's latitude: size it with cos(lat).
- Time zones are worked out OFFLINE (`Timezones`): the browser's zone when it belongs to the place's country, else the state's zone by ISO code (`RegionZones`: US, CA, AU), else PHP's zone data scored by distance + offset.
- Trips notify members within the admin's radius (`trip_radius_km`, default 160, clamped 10–1000) up to `trip_max_alerts` (default 50, clamped 1–200) (`Trips::notify`, bounding box + distance). Meetups start a discussion through Flarum's API as the member (process() skips `startDiscussion` and the tag check: both are asked by hand) and go on Calendar when it's enabled.
- The map endpoint refuses crawlers (`Api\Crawlers`) and the page is noindex unless the admin allows it. `members_only` places never reach guests (map or profile).
- Marker and popup content is built with DOM text / Mithril, never HTML strings: names must never become HTML.

## Testing

- `composer test:setup && composer test` (integration; run SQLite, MySQL and PostgreSQL with DB_DRIVER set), `composer analyse:phpstan`. require-dev has flarum/tags, flarum/suspend, ianm/follow-users (+ fof/follow-tags) and ernestdefoe/calendar so each integration is tested for real.
- `cd js && npm ci && npm run build && npm run format-check && npm run check-typings`.
- JS entries are `js/forum.ts` / `js/admin.ts` (`export * from`), declarative extenders in `js/src/<frontend>/extend.ts`. The map page's parts live in `components/mapPage/` and are imported ONLY from MapPage (any other importer splits them into a numbered chunk). Functions stay under 50 lines; `.catch(shown)` after `call()`/`save()`, never an empty catch or `console.*`.
